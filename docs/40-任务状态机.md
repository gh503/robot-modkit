# 40 · 任务状态机（M4 软件骨架）

> 把"导航 → 找 → 抓 → 搬 → 放"串起来，并且把重试/超时/失败原因做成可测的逻辑。
> 状态机不碰硬件，四个动作由调用方注入，所以仿真、真机、回放共用一套流程。

## 1. 状态流

```
nav_pick:try1 ──失败──> nav_pick:try2 ──失败──> 中止（导航失败）
     │成功
look:1 ──没看到──> 原地转 90° ──> look:2 … 最多 search_turns 次
     │看到
pick:try1 ──失败──> pick:try2 ──失败──> 中止（抓取失败）
     │成功
nav_drop:try1 ──失败──> nav_drop:try2 ──失败──> 中止
     │成功
drop ──失败──> 中止
     │成功
完成
```

代码：`software/modkit/mission.py`；CLI：`modkit --sim mission`。

## 2. 接口

| 注入动作 | 签名 | 说明 |
|---|---|---|
| `drive_to` | `(x, y, theta) -> bool` | 导航到点位，返回是否到达 |
| `look` | `() -> Detection \| None` | 当前视野里找目标 |
| `pick` | `(det) -> bool` | 抓取，返回是否夹住 |
| `drop` | `() -> bool` | 放置 |

配置：`pick_xy`、`drop_xy`、`max_seconds=180`、`search_turns=4`、`retries=1`。

## 3. 仿真结果

```bash
modkit --sim mission
```

```
nav_pick:try1
look:1
pick:try1
nav_drop:try1
drop
PASS：完成，16.4s，动作 3 次
```

（仿真里导航按 `nav.drive_to` 的用时，look 0.5s，抓取 4s，放置 2s。）

## 4. 多任务队列

```bash
modkit --sim mission --tasks "200,0,-150,0;200,100,-150,100"
```

- 每个任务独立跑一遍 `Mission`，重新用它的 pick/drop；
- 任一任务失败就停，保留前面每一步结果；
- 总预算默认 600s，单任务最多 180s；
- 输出 JSON：`tasks`、`seconds`、每个任务的 `success/reason/states`。

仿真实测：2 个任务 **34.6s**，任务 1 `16.4s`、任务 2 `18.2s`。

## 5. 测试覆盖

| 场景 | 结果 |
|---|---|
| 正常流程 | 5 个状态，2s+... 16.4s，成功 |
| 前两次没找到，第三次找到 | `look:3`，成功 |
| 第一次抓失败，重试成功 | `pick:try2`，动作 4 次 |
| 导航两次都失败 | 中止，原因"导航到抓取点失败" |
| 转完仍没目标 | 中止，原因"没找到目标" |
| 超时 | 中止，原因含"超时" |

9 项测试（含队列 2 任务、失败即停、总预算），`tests/test_mission.py`。

## 6. 还没做的

- **地图/定位**：仿真里位姿直接给，真机要靠里程计 + 标记/视觉；
- **动态障碍**：现在只按固定点位走；
- **错误恢复**：只覆盖重试/超时，没有"被抓物掉落""电量低""急停后恢复"；
- **真实时序**：仿真里抓取 4s 是常数，真机要看舵机速度/夹爪电流；
- **任务依赖/优先级**：队列是顺序执行，没有并行或抢占。

前四项都需要真机或更细的仿真，标为后续迭代。
