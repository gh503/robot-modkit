# 00 · 项目计划

> 一句话目标：**造出一台能自己完成"取物—搬运—放置"的机器人**，并且这条路径上的每一步
> 都能被验证、被回退、被替换。

## 1. 把"能独立执行物理任务"定义清楚

模糊的目标会毁掉项目。本项目的验收任务书写死如下：

> **任务 T1（M4 验收）**
> 机器人在房间一角待机。人把 40mm 红色方块随机放在桌面 A 区的 3 个位置之一，
> 托盘在 2 米外的 B 区。按下启动键后，机器人**无人干预**完成：
> ① 从待机点导航到 A 区视线范围 → ② 找到方块 → ③ 抓取 → ④ 导航到 B 区 →
> ⑤ 放入托盘 → ⑥ 返回待机点。
> **5 次机会，成功 ≥ 4 次，单次 ≤ 3 分钟，中途不许人手扶。**

这个任务包含：定位、导航、避障、视觉识别、手眼标定、逆运动学、抓取、状态机、错误恢复。
它比"跳舞机器人"难得多，但**每一块都能单独测**——这就是它适合做目标的原因。

> 软件侧完成度与物理闸门逐条对照见 [42-完成度审计](42-完成度审计.md)。

## 3. 三条工程纪律

### 3.1 每层留证据，不留"应该能行"

| 层 | 证据形式 | 判据 |
|---|---|---|
| 机械 | `cad/build.py` 的断言 | 干涉体积 = 0、间隙 ≥ 设计值、STL 水密 |
| 协议 | 逐字节对比官方示例 | 帧格式错一个 bit 就红 |
| 运动学 | 正解↔逆解往返 | 误差 < 0.5mm |
| 平台 | 真机日志 | 扫描率、丢包率、电压曲线 |
| 任务 | 成功率 | 5 次 ≥ 4 次 |

**没有证据的功能 = 不存在。** README 的状态表只写有证据的。

### 3.2 一次只改一个变量

改结构就不改固件，改固件就不改结构。否则失败时不知道是谁的错。
每次改动后跑：`cd cad && build.py` + `cd firmware && make test` + `pytest`。

### 3.3 先降级，再优化

- 抓不稳 → 先把速度降到 1/3，确认是力不够还是姿态错
- 导航飘 → 先用贴纸做人工地标，确认是编码器问题还是地图问题
- 视觉认错 → 先只认一种颜色，再加形状

## 5. 迭代回路（每天 30 分钟就够）

```
现象（机器人做了什么） 
  → 归类（机械 / 电气 / 固件 / 算法 / 任务逻辑）
  → 最小复现（一条命令能重现吗？）
  → 加断言（让它以后再也不会悄悄坏）
  → 修复 → 回归（三套测试全绿）
  → 记一条日志
```

日志模板（放 `docs/logbook.md`，一天一行）：

```
2026-11-02 | M1 | 肘关节过中点后自锁 | 机械 | 肘角 0° 附近齿轮间隙 | 加 2mm 垫片 | 复测 OK
```

## 7. 风险与退路

| 风险 | 触发信号 | 退路 |
|---|---|---|
| 机械精度不够，抓取总偏 | 标定后仍偏 > 1cm | 换铝制舵盘/CNC 件；或降低抓取精度要求（更大目标物） |
| 打印件蠕变导致关节松 | 一周后重复精度变差 | 关键件换 PETG-CF 或尼龙；加金属衬套 |
| 视觉在室内光线下不稳 | 白天成功、晚上失败 | 加补光/改用 ArUco 标记；先做"有标记"版本 |
| 舵机堵转烧毁 | 电流飙升、温度 > 70℃ | 软件限流 + 机械限位 + 保险丝；备 1 只舵机 |
| 业余时间断档 | 两周没动 | 每个里程碑都有"可停可续"的检查点；文档写得让三个月后的自己能接上 |
