# 13 · 业界实践对照与优化清单

> 目的：不要凭感觉"再优化一点"，而是拿同类项目与通用规范当尺子，量出差距、排优先级。
> 调研时间 2026-10-25。引用链接都在文末，能点开核对。

## 0. 三条结论（先看这个）

1. **最便宜的失败预防不是更好的设计，而是"先打一个校准件"**。SO-ARM100 在 STL 里专门放了
   Gauges 目录：先用 15 分钟打一块量具，确认孔径和舵机宽度，再打整机。我们之前是直接打 12 个零件。
2. **控制环缺的不是更高增益，而是前馈和抗饱和**。把 `kp` 从 0.8 提到 2.0 只能让误差变小、
   震荡风险变大；加前馈（补 1/0.85）和反算抗饱和，才是"不改硬件就变好"的部分。
3. **文档要分层，不是越多越好**。新手要"照着做能成"，开发者要"接口是什么"，维护者要"为什么这么定"。
   现在 12 篇是混着写的，新人第 3 篇就会迷路。

## 4. 需要你拍板的两件事

1. **许可证**：现在是 MIT（代码 + 图纸 + 文档一把梭）。业界常见做法是
   **代码 MIT / 硬件 CERN-OHL-W / 文档 CC-BY-SA-4.0** 三分。
   好处：别人改了你的图纸必须回馈（OHL 的"相互性"）；坏处：商用门槛变高，可能劝退小厂。
   **我的建议**：保持 MIT 到有人真的想商用为止 —— 现阶段目标是"有人愿意照着做"，不是"防着别人"。
2. **安全件**：物理急停按钮（约 ¥10，常闭按钮串在 12V 主回路）是否进 M1.1 BOM。
   **我的建议**：进。软件卸力挡不住"上位机死机 + 舵机抽风"同时发生。

## 5. 下一步优先级（按"性价比"排，不按"想不想做"）

| 优先级 | 事项 | 工作量 | 为什么现在做 |
|---|---|---|---|
| P0 | 依赖锁定 + Python 版本声明 | 0.5h | 别人 clone 下来跑不起来，前面全白做 |
| P0 | 物理急停进 BOM 与装配图 | 1h + ¥10 | 唯一能兜住软件失效的手段 |
| P1 | 文档导航（Diátaxis 标注） | 1h | 新人第 3 篇迷路是真实流失点 |
| P1 | `modkit calibrate` 向导 | 3h | 把 G7 从"看文档手动做"变成"一条命令" |
| P1 | 爆炸图 + 每零件摆放建议 | 2h | 装配失败的第一大原因是方向/支撑 |
| P2 | 协议 fuzz + Web Serial e2e | 4h | 已有真机后才值得投入 |
| P2 | 205×250 / 256×256 拼盘 | 1h | 有打印机的人床不一样 |
| P3 | OSHWA 认证 | 钱 + 时间 | 现阶段没有分发需求 |

**明确不做**（避免过度工程）：ROS 2 集成、MoveIt 配置、云端数据集、自动装箱算法、CI 里跑真机。
